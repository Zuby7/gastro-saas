## Ticket #7 fix cycle 1 (Opus CHANGES_REQUESTED, `artifacts/reviews/issue-7.json`)

- **Auth rate-limit key scheme**: changed from "email alone" (plus IP alone) to "IP alone" AND "(IP, email) combination" -- never email alone. Email-alone keying let any anonymous third party lock a _known victim's_ email out of login for a whole window just by submitting `maxAttempts` failed attempts against it (optionally rotating source IPs to also dodge the IP-only bucket); the attacker's cost was "know the victim's email", not "control a fixed IP". Keying on `(ip, email)` instead still fully stops a single attacker IP from brute-forcing one account or cycling through many, while never fully denying the victim's own login from their own, different IP. A fully distributed attacker spraying attempts across many IPs against one victim is a harder problem this scheme does not fully solve (each new IP gets its own fresh `(ip, email)` bucket) -- accepted for this fix cycle; a CAPTCHA/step-up challenge would be the next layer if this is ever observed in practice. See `apps/web/src/lib/auth/rate-limit.ts`.
- **Only failed attempts count** toward the rate limit (previously: successes counted too, so a legitimate user could lock themselves out after `maxAttempts` successful logins in the window). Implemented via an atomic reserve-then-mark-succeeded pattern (`reserve_auth_rate_limit_attempt` / `mark_auth_rate_limit_attempt_succeeded`, `supabase/migrations/20260801070000_auth_rate_limit_atomic_and_login_audit_rpc.sql`) rather than a separate check-then-act pair of queries, closing a race where concurrent requests could all observe a stale "under the limit" count.
- **`auth.email.enable_confirmations` production posture (item 5)**: option (a) was chosen -- tenant creation is deferred to the user's first confirmed sign-in rather than requiring a documented "keep confirmations off" workaround. `registerAction` now handles a `signUp()` response with no session (the shape `enable_confirmations = true` produces) by returning an informational message instead of a dead-end error; `/account`'s zero-tenant-membership fallback (`createTenantAction`, ticket #7 fix cycle 1 item 4) completes onboarding on that first login. Local dev still runs with `enable_confirmations = false` (`supabase/config.toml`) for faster iteration and the existing E2E/integration tests that assume an immediate session -- but the production code path for the `true` case is implemented and covered by a unit test (`apps/web/src/app/register/actions.test.ts`), not merely documented as a gap.
- **E2E-in-CI status reaffirmed, not changed**: `apps/web/playwright.config.ts` already documented that the Playwright suite is local-only (needs `supabase start` + a running Next.js server together, no CI job currently provisions both). That decision stands after this fix cycle -- both E2E specs (`apps/web/e2e/login.spec.ts`) were run locally against the real local Supabase stack as part of validating this fix cycle and pass, but CI wiring remains a follow-up (`docs/testing/test-strategy.md`'s "E2E smoke" gate).
- **`apps/web`'s Vitest config now aliases `@/*` to `./src/*`** (`apps/web/vitest.config.mts`), mirroring `tsconfig.json`. Needed to write action-level tests for `loginAction`/`registerAction` (ticket #7 fix cycle 1 item 7), which import their dependencies via that alias -- Vite/Vitest doesn't read tsconfig `paths` without an explicit alias or plugin.

## Epic 7 batch review, cycle 2 — fixed in-place, plus residual risks

The one HIGH finding (refund double-refund gap: an `unconfirmed` refund only blocked further attempts via the aggregate amount check, not via its own existence, so a second smaller partial-refund attempt against the same payment could still reach Stripe) and 3 cheap SHOULD-fixes were all fixed in-place this cycle (`ensure_refund_matches_payment_and_within_limit()`'s new existence check; `apply_connect_account_snapshot()`'s `onboarding_completed_at` coalesce; a live-database test for `claim_payment_webhook_event()`; `isDefinitiveStripeFailure()` now classifies `StripeRateLimitError` as definitive). Two smaller findings were judged genuine but not urgent enough to block this cycle, and are tracked as follow-up issues rather than silently deferred:

- **No mutual-exclusion lock documented for `claim_payment_webhook_event()` (issue #91)**: two truly concurrent deliveries of the same Stripe event id could both observe `already_processed = false` in the brief window between the RPC's own `insert ... on conflict` and either caller finishing its own processing — currently harmless in practice because every downstream operation this RPC guards (`apply_connect_account_snapshot()`, the payment webhook's order/payment updates) is itself idempotent, but this safety net is implicit, not documented or enforced by a lock. Issue #91 tracks either adding an explicit advisory lock or writing this reasoning down as a deliberate, reviewed design decision.
- **Orphaned Stripe Express account on insert failure (issue #92)**: `startStripeOnboardingAction` creates the Stripe Express account first, then writes the `payment_accounts` row via the service-role client — if the DB write fails after the Stripe account was already created, the tenant is left with a real (test-mode) Stripe Express account with no corresponding local record, and a retry creates a second orphaned Stripe account rather than reusing the first. Low impact in test mode (no real payouts), but issue #92 tracks either a reconciliation step or a two-phase create that avoids the orphan.
