# Deployment Strategy

## Environments

| Environment | Trigger                           | Approval                                                                                              |
| ----------- | --------------------------------- | ----------------------------------------------------------------------------------------------------- |
| Local       | `pnpm dev`                        | none                                                                                                  |
| Preview     | every PR                          | automatic                                                                                             |
| Staging     | manual promotion from a merged PR | automatic, run `/release-check` first                                                                 |
| Production  | explicit request                  | **always requires explicit human approval** — both the deploy itself and any migration run against it |

## Hosting

Cloudflare Pages/Workers via `@opennextjs/cloudflare` (see ADR-0001, `docs/platform/service-register.md`). Free `*.pages.dev`/`*.workers.dev` subdomain until a real domain is purchased (a deliberate later step, not part of this foundation pass).

### Middleware-manifest 500 bug — fixed (2026-09-06)

The blocker described in the "First deployment attempt" section below (`Dynamic require of "/.next/server/middleware-manifest.json" is not supported`, every request 500ing) is now fixed and the app is live. Root cause and fix, confirmed against upstream:

- **Root cause, confirmed via the upstream tracker**: `next@16.2.12`'s `next-server.js`'s `getMiddlewareManifest()` calls raw `require(this.middlewareManifestPath)`, which workerd doesn't support. `@opennextjs/aws` (the underlying engine for `@opennextjs/cloudflare`) already ships an AST-based build patch (`patchNextServer.js`'s `removeMiddlewareManifestRule`) that rewrites this method's body to `return null;` at build time, and OpenNext's own middleware handling doesn't actually depend on this method at all — the real middleware manifest is inlined as a plain JS object literal directly into the separate `.open-next/middleware/handler.mjs` bundle it builds for the Edge-style middleware runtime. In this app's case the crash still reproduced at runtime despite that existing patch (matching the still-open, still-unresolved upstream reports opennextjs/opennextjs-cloudflare#1380, created 2026-09-03, and #1232 — both confirmed open with **no released fix**, including in the current `latest`, `@opennextjs/cloudflare@1.20.6` published 2026-09-02, which #1380 itself reproduces against).
- **No newer adapter version fixes this**: checked npm/GitHub releases up to `@opennextjs/cloudflare@1.20.6` (latest as of 2026-09-06) — none post-date or reference a fix for #1380/#1232, and #1380 explicitly reproduces on `1.20.6`. `1.20.6` also requires `next >=16.3.3`, which is not what this app is pinned to (`16.2.12`), so upgrading was not an available option even if it had fixed the issue. Stayed on `@opennextjs/cloudflare@1.20.2`.
- **Fix applied — documented upstream patch via `pnpm patch`**: issue #1380's own "Workaround" section documents patching `next`'s `getMiddlewareManifest()` to call `(0, _loadmanifestexternal.loadManifest)(this.middlewareManifestPath)` instead of the raw `require()`, reusing the same `loadManifest()` helper that `getPagesManifest()`/`getAppPathsManifest()` already use (and that `@opennextjs/aws`'s separate `inlineLoadManifest` build patch already covers). Applied exactly that documented change via `pnpm patch next@16.2.12` / `pnpm patch-commit`; tracked as a normal repo artifact at `patches/next@16.2.12.patch`, referenced from `pnpm-workspace.yaml`'s `patchedDependencies`. No invented patch logic — this is the literal upstream-documented fix.
- **Build verification**: `pnpm --filter @gastro-saas/web run build:cf` succeeds; the patched `next` package (`node_modules/.pnpm/next@16.2.12_patch_hash=...`) is what's bundled into `.open-next/server-functions/default`; `getMiddlewareManifest()` in that bundled copy is further overwritten to `return null;` by `@opennextjs/aws`'s own build-time patch (harmless and expected — that method isn't on the path OpenNext's middleware runtime actually uses; see root-cause note above).
- **Auth-middleware verification (not just "no more 500")**: `apps/web/src/middleware.ts` (Supabase session-refresh middleware, `matcher: ["/((?!_next/static|_next/image|favicon.ico).*)"]`) is bundled into `.open-next/middleware/handler.mjs` — confirmed present (Supabase `getUser()`/cookie-handling code found in that bundle) and confirmed **zero** `require(` calls in that bundle. The middleware manifest itself is inlined as a static JS object (`var MiddlewareManifest = {...}`) in that same bundle, matching the app's real matcher config — not read via `require()` at runtime. Live-request checks via a redacted `wrangler tail` session (no secrets or tokens ever printed) during real HTTPS requests to `/`, `/login`, and the protected `/account` route (both with no cookie and with a fake session cookie) show every request logged `Ok` with no thrown exception; `/account` correctly 307-redirects to `/login` for the unauthenticated/invalid-session case, i.e. the middleware's Supabase code path actually executes and the app's auth-gating behaves as designed. Note: `NEXT_PUBLIC_SUPABASE_URL` is still the local-dev-only placeholder (`http://127.0.0.1:54321`, baked into the bundle at build time per the pre-existing "Env vars / secrets" gap below) — the deployed Worker's `getUser()` call can't reach a real local Supabase instance, but the SDK handles that network failure gracefully (returns `no user`, no crash) rather than throwing, so this doesn't block confirming the middleware code path itself runs correctly. Once real Supabase project credentials exist (separate, already-tracked follow-up), a full logged-in-session check should be re-run.
- **Live URL reachability, reconfirmed**: `https://gastro-saas-web.gastro-saas-web.workers.dev` returns a real HTTP 200 for `/` over **both HTTP and HTTPS** (the TLS cert propagation noted below has completed — `curl -v` shows a valid TLS 1.3 handshake, `subject: CN=gastro-saas-web.workers.dev`, and `x-opennext: 1` response header confirming the real deployed Worker answered).
- **Deterministic checks re-run after the patch**: `lint` (added a missing `.open-next/**` ignore to `apps/web/eslint.config.mjs` — the Cloudflare build output was being linted as source, a pre-existing gap from the original Cloudflare setup, not part of this fix's own logic but blocking a clean lint run), `typecheck`, and `test` (51 files / 307 tests) all pass.

### First deployment attempt (2026-09-06) — infra live, app currently broken (BLOCKED)

- **Adapter**: `@opennextjs/cloudflare@1.20.2` + `wrangler@4.129.0`, pinned deliberately below the installed `next@16.2.12`'s actual peer-compatible ceiling (`@opennextjs/cloudflare@1.20.6`, the `latest` at install time, requires `next >=16.3.3`; upgrading Next itself was out of scope for this deployment-prerequisite ticket).
- **Config added**: `apps/web/wrangler.jsonc` (Worker name `gastro-saas-web`, `compatibility_date: 2024-09-23`, `nodejs_compat` flag, static assets binding), `apps/web/open-next.config.ts` (default `defineCloudflareConfig()`), `initOpenNextCloudflareForDev()` added to `apps/web/next.config.ts`, `build:cf`/`preview:cf`/`deploy:cf` scripts added to `apps/web/package.json`. `.open-next/` and `.wrangler/` added to `.gitignore`.
- **Build command**: `pnpm --filter @gastro-saas/web run build:cf` (wraps `opennextjs-cloudflare build`) — succeeds locally after clearing a stale `.next/` cache left over from an earlier `next dev` run (an unrelated pre-existing stale-cache issue, not an adapter problem).
- **Deploy command**: `pnpm --filter @gastro-saas/web run deploy:cf` (wraps `opennextjs-cloudflare deploy`), run with `CLOUDFLARE_API_TOKEN` set as a process environment variable (never a CLI arg), sourced from the repo-root `.env` (gitignored).
- **Cloudflare project**: Worker (not classic Pages — current `@opennextjs/cloudflare` docs deploy Next.js as a Worker with a static-assets binding, which is now the recommended/only actively-maintained path; "Cloudflare Pages/Workers" in the service register covers this). Name `gastro-saas-web`, account subdomain auto-registered as `gastro-saas-web` (no prior workers.dev subdomain existed on this account) → live URL **`https://gastro-saas-web.gastro-saas-web.workers.dev`**.
- **Deploy-time fix needed**: the first deploy attempt failed with Cloudflare API error 10021 ("Can't set compatibility date in the future") against the initially-chosen `compatibility_date` (today's date per this machine's system clock) — Cloudflare's edge evidently runs slightly behind. Fixed by pinning `compatibility_date: "2024-09-23"` (a safely-past, `nodejs_compat`-eligible date) instead of "today".
- **Verification** (2026-09-06): `curl`/PowerShell `Invoke-WebRequest`/Python `urllib` all fail an HTTPS **TLS handshake** (`SSLV3_ALERT_HANDSHAKE_FAILURE`) against the workers.dev URL as of this writing — plain **HTTP** to the same host succeeds and is answered by the real deployed Worker (`x-opennext: 1` response header, confirming the deploy is genuinely live at the edge), so this looks like a still-propagating TLS cert for the brand-new account subdomain rather than a broken deploy; **re-verify HTTPS once more before relying on this URL**, it was not yet confirmed working over HTTPS in this pass.
- **Real, confirmed blocker — every request 500s**: `wrangler tail` shows `Error: Dynamic require of "/.next/server/middleware-manifest.json" is not supported` on every request. This is a **known, open upstream bug** in `@opennextjs/cloudflare` (confirmed via its own GitHub issue tracker: opennextjs/opennextjs-cloudflare#1380, #1232 — `next-server.js`'s `getMiddlewareManifest()` does a raw `require()` that isn't covered by the adapter's manifest-inlining patch, unlike `getPagesManifest()`/`getAppPathsManifest()`). It reproduces for "basically any Next 16.x app" with a non-trivial middleware manifest — this app has one (`apps/web/src/middleware.ts`, the Supabase auth session-refresh middleware). The only workaround documented upstream is an unofficial `pnpm patch` directly on `next`'s own `next-server.js` internals — deliberately **not applied** here without the user's explicit sign-off: it patches a core framework file (fragile across Next upgrades) and the affected code path is the auth session-refresh middleware, which falls under this project's "elevated security scrutiny near auth" rule. **Deployment is therefore BLOCKED at the application-runtime level pending one of**: (a) an upstream adapter fix/release, (b) explicit user approval to carry the unofficial `next-server.js` patch, or (c) an explicit user decision to temporarily ship without the session-refresh middleware (accepting a real auth UX regression) until (a) or (b).
- **Env vars / secrets**: none set as Cloudflare Worker secrets yet — this repo's own `.env` only has a real `CLOUDFLARE_API_TOKEN` value; `NEXT_PUBLIC_SUPABASE_URL`/`SUPABASE_SERVICE_ROLE_KEY`/Stripe/Resend keys in `.env.example` are all local-dev placeholders or well-known local Supabase defaults, not real hosted-project credentials, per explicit instruction not to invent secrets. **Manual follow-up needed**: once real Supabase/Stripe/Resend projects exist, set their values via `wrangler secret put <NAME>` (never committed, never a Pages/Workers *plaintext* var for anything server-side-sensitive).

### Real Supabase project wired in, redeployed, migrations blocked (2026-09-06)

- **Cloudflare Worker secrets confirmed** (`wrangler secret list`, names only — no values ever printed): `SUPABASE_SERVICE_ROLE_KEY` is set as a runtime secret on `gastro-saas-web`. This is the only server-side-sensitive var the app needs (`apps/web/src/lib/supabase/admin.ts`) — `NEXT_PUBLIC_SUPABASE_URL`/`NEXT_PUBLIC_SUPABASE_ANON_KEY` are build-time-inlined public values, not runtime secrets, so they don't need `wrangler secret put`.
- **Rebuild + redeploy against the real project**: `PROD_SUPABASE_URL`/`PROD_SUPABASE_PUBLISHABLE_KEY`/`PROD_SUPABASE_SECRET_KEY` (repo-root `.env`) were mapped to the app's actual expected build-time env var names (`NEXT_PUBLIC_SUPABASE_URL`/`NEXT_PUBLIC_SUPABASE_ANON_KEY`/`SUPABASE_SERVICE_ROLE_KEY`) via a small Node wrapper script that reads `.env` and injects them only into the child process's environment (never printed, never written into `apps/web/.env.local`, which stays on local-dev placeholders on purpose). `pnpm run build:cf` then `pnpm run deploy:cf` succeeded: `https://gastro-saas-web.gastro-saas-web.workers.dev`, Version ID `5e82b7fd-4e0d-4543-980a-c10a4ddce632`. Two earlier build attempts failed with a transient `fetch failed` / `ECONNRESET` during `next build`'s static-generation phase reaching the real Supabase project (this incidentally confirms the build was genuinely targeting the real hosted project, not the local placeholder) — the third attempt succeeded with no code change, i.e. a transient network blip, not a real defect.
- **Connectivity verified via `wrangler tail`** (redacted, no secrets/tokens printed) during real HTTPS requests to the live URL: `/` and `/login` return 200 (`Ok`), `/account` returns a 307 redirect to `/login` (unauthenticated), `/r/trattoria-da-mario` returns 404 (expected — no tenant data exists yet, migrations not applied). No thrown exceptions in any of these; the middleware's Supabase call path executes against the real project's URL.
- **Migrations against the real project: BLOCKED, needs the DB password (and a Supabase CLI access token)**. `supabase link --project-ref <ref derived from PROD_SUPABASE_URL>` fails immediately with `LegacyPlatformAuthRequiredError` — the Supabase CLI first needs an **account-level personal access token** (`supabase login` or `SUPABASE_ACCESS_TOKEN`) before it will even prompt for the project DB password, and neither that access token nor the DB password exists anywhere in this repo's `.env`/`.env.example` (the DB password is set once at project creation in the Supabase dashboard and was never captured here, per explicit instruction not to invent or guess it). Per explicit instruction, this step was stopped rather than worked around — no login flow attempted, no password guessed. **Seeding is blocked for the same reason** (`supabase/seed.sql` + `upload-dish-media.mjs` need a real `SUPABASE_DB_URL` against the linked project). **End-to-end menu-page verification for `trattoria-da-mario` is therefore also blocked** — the live Worker is reachable and reaches the real (empty) Supabase project, but there is no tenant data yet for that slug to render.
- **Manual follow-up needed from the user**: supply either (a) a Supabase CLI personal access token (`supabase login` in an interactive session, or set `SUPABASE_ACCESS_TOKEN`) plus the project's DB password, so `supabase link` + `supabase db push` + seeding can run, or (b) run the migration/seed directly via the Supabase dashboard's SQL editor as an alternative. Credential rotation for `CLOUDFLARE_API_TOKEN` (flagged in a prior pass, see `docs/decisions/assumptions.md`) is unchanged and still pending — explicitly deferred by the user for this pass.

## Database migrations

- Every schema change ships as a migration file + its RLS policy in the same migration.
- Migrations run automatically against local/preview/staging.
- Migrations against production require explicit approval and a documented rollback note in the PR.

### Local development (Supabase CLI)

- The Supabase CLI is a dev dependency of `packages/database` (npm package `supabase`, installed via `pnpm install` -- no global/admin install needed, matching how `pnpm`/`gh` were installed on the dev machine per `docs/decisions/assumptions.md`), invoked as `pnpm --filter @gastro-saas/database exec supabase <command>` or via the package's `db:*` scripts (`db:start`, `db:stop`, `db:reset`, `db:seed`, `db:lint` -- `db:reset`/`db:seed` wrap the local demo-seed opt-in guard, see `docs/decisions/assumptions.md`'s "Local dev demo seed data" section).
- `supabase start` runs the full local stack (Postgres, Auth, Storage, Studio, etc.) via Docker and applies every migration under `supabase/migrations/` in filename order. `supabase stop` frees the Docker resources afterwards.
- Migration file naming convention: `supabase/migrations/<YYYYMMDDHHMMSS>_<snake_case_name>.sql` (Supabase CLI default ordering).
- `supabase/migrations/20260801040000_tenant_membership_brand_location_model.sql` (ticket #4) is the real tenant/membership/brand/location schema and the pattern to copy for further tenant-scoped tables: explicit `tenant_id` + RLS policy in the same migration. The earlier `20260801030000_example_tenant_isolation_pattern.sql` was a disposable reference-only migration (no real domain table) and has been superseded -- don't copy it for new work, but its comments on what it does _not_ cover (Layer 0 / guest paths) still apply and are covered in `docs/security/tenant-isolation.md`.
- `supabase/seed.sql` is the seed-script skeleton run by `supabase db reset`; currently a no-op until real domain tables exist.
- CI validates migrations via `.github/workflows/migration-check.yml`, which runs `supabase start` (applies all migrations against a fresh local Postgres) followed by `supabase db lint` on every PR touching `supabase/**`.
- Local env vars live in `.env.example` at the repo root; copy to `.env.local` and the values already match Supabase's well-known local-dev defaults -- no manual key lookup needed for local work.

## Background processing

No dedicated queue system in the MVP. Email delivery, webhook handling, retryable integration sync, analytics aggregation, and scheduled availability changes use the simplest reliable mechanism the platform supports (Supabase Edge Functions / scheduled functions, Next.js route handlers). A dedicated queue is introduced only when a measured requirement justifies it (§13.4 of the source brief).

## Observability

- Errors: Sentry (free Developer tier — see service register).
- Uptime: Better Stack (free tier — see service register for why UptimeRobot was rejected).
- Product usage (of the SaaS app itself, not restaurant sales): PostHog.

## Backups (free-tier — resolves a contradiction flagged by the Opus architecture review)

Supabase's free tier includes no managed backups. Since the user requires an entirely free setup, production backups are a scheduled GitHub Actions job (within the free 2,000 min/month budget) running `pg_dump` against the Supabase database and uploading the encrypted dump to a Cloudflare R2 bucket (R2 free tier: 10 GB storage, no egress fee — same Cloudflare account already used for hosting). A restore is tested at least once before the first real pilot tenant goes live, and that test is itself a `/release-check` item, not assumed to work.

## Release checklist (`/release-check`)

Before any staging→production promotion: migrations validated, environment variables verified, observability wired up, the free-tier backup job has a verified recent successful run and a tested restore, smoke tests green. Never deploys to production itself — it only validates readiness; the actual production deploy always needs separate explicit human approval.
